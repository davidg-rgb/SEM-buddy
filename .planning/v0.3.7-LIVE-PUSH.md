## 3. Bug #1 — resume snapshot GAQL missing `campaign.id` in SELECT (ship-blocker)

`_build_resume_state` issued five GAQL queries that filtered `WHERE campaign.id = X`
**without** selecting `campaign.id`. Google Ads API v23 rejects this with
`EXPECTED_REFERENCED_FIELD_IN_SELECT_CLAUSE` ("The following field must be present
in SELECT clause: 'campaign.id'"). The resume path died on the very first query, so
**resume never worked** despite shipping with 5 green tests.

The same defect existed in the `apply-bids` ad-group lookup (`WHERE campaign.name`
without selecting `campaign.name`) — so the daily-cron bid-refresh command was also
broken.

**Why the tests missed it:** the fake `search`/`search_stream` accepted any GAQL
string. **Fix:** added `campaign.id` / `campaign.name` to all six SELECT clauses,
and gave the test fake a `_validate_gaql` checker that replicates Google's real
rule — *a WHERE field whose resource prefix differs from the FROM resource must be
selected* (confirmed empirically against v23: same-resource enum filters like
`ad_group_ad.ad.type` are fine without selection). Any future SELECT/WHERE mismatch
now fails the unit tests.

Files: `src/apis/campaign_pusher.py` (6 queries), `tests/test_campaign_pusher.py`
(`_validate_gaql` + 3 tests).

## 4. Bug #2 — resume asset-skip detection compared enum NAME to numeric value

`_build_resume_state` did `ft = str(row.campaign_asset.field_type)` then
`if "SITELINK" in ft`. But `str(field_type)` is the **numeric** enum value
(`"13"`), never the name `"SITELINK"`. So `has_sitelinks/callouts/promotions` were
**always False** → resume re-created every asset and every asset link on each run.
Additionally, promotions link at the **ad-group** level (`ad_group_asset`), but the
snapshot only queried `campaign_asset` — so promotions were doubly undetectable.

**Symptom:** a diagnostic resume re-run created **951 duplicate assets** (campaign
assets 8→16, ad-group promotions 943→1,886).

**Fix:**
- Match on `field_type.name` (canonical SDK accessor), not `str()`.
- Snapshot promotions from `ad_group_asset` and skip them **per ad group**
  (`existing_promotion_ag_rns`), not via a single bool — a quota-kill mid-promotions
  would otherwise strand ad groups that never got one and a bool would skip them
  forever. `_push_promotions` gained a `skip_ag_rns` parameter.

Files: `src/apis/campaign_pusher.py` (`_ResumeState.existing_promotion_ag_rns`,
`_build_resume_state`, push loop, `_push_promotions`),
`tests/test_campaign_pusher.py` (2 rewritten/new tests).

## 5. Cleanup of the 951 duplicate assets

`scripts/dedupe_campaign_assets.py` (new) collapses each duplicated asset group to
one link — by content for campaign assets, by ad group for promotions. It tallies
`response.results` so it reports what Google **actually** removed, not what was
requested.

The cleanup is what surfaced the GAQL-search-staleness trap (§1): the first dedup
run succeeded but `search` kept showing the duplicates, which led to a diagnostic
that **over-removed** PKC's (`Petropavlovsk-Kamchatsky`, ad group `196433361523`)
sole remaining promotion. It was restored directly via `_push_promotions` (asset
`364772311482`), verified present via `validate_only`. Net: every ad group has
exactly one promotion.

## 6. The 991 rejected RSAs — diagnosed, fixed, recovered to 100%

Of 4,580 planned RSAs, the first resume landed 3,589; **991 were dropped by
`partial_failure`** with "policy summary includes policy topics of type
PROHIBITED." `partial_failure` errors don't carry `policy_finding_details`, so
`_extract_policy_topics` (added this session) returned empty. The fix: a
`validate_only` create (no partial_failure) of a rejected variant raises a full
`GoogleAdsException` that **does** carry the topic — `scripts/diagnose_rsa_policy.py`
does exactly this. It named the topic immediately:

### 6a. `SYMBOLS` — the ★ glyph (963 of 991)

The diagnostic returned `SYMBOLS` on every probed variant. Root cause: the
BLACK STAR `U+2605` in the social-proof Trustpilot copy ("4.5★ on Trustpilot",
"Price-match guarantee on {name}. 4.5★ Trustpilot…") — **1,926 occurrences
across all 963 ad groups' social_proof variant**. Google's RSA SYMBOLS policy
prohibits decorative glyphs. **Fix:** replaced every `★` with `4.5/5` in
`data/en/ad_copy_patterns.json` (→ pack v4.2) and `src/generators/llm_ad_copy.py`.
Re-running the diagnostic after the fix: all probed variants pass `validate_only`.
Re-push landed **947** of the 991.

### 6b. Duplicate headline (44 of 991)

The remaining 44 then failed with "Assets are duplicated across operations" at
`headlines[14]` — even one-op-per-request, so the duplication was **within** the
RSA. All 44 were long-name discounted destinations (Thiruvananthapuram,
Galapagos Islands, …) whose discount_led variant carried `"Save X% on {name}"`
**twice**. Root cause: `_add` stores dedup keys as `text.casefold()`, but the
mandatory/top-up discount force-injection blocks checked/stored the **raw**
`forced` text — so a casefolded pattern headline slipped past the forced line.
**Fix:** normalized those force-injection dedup checks to `.casefold()`
(`generate_headlines_for_variant`). Re-push landed the final **44** → **4,580/4,580**.

### Guards added
- `tests/test_rsa_variants.py::test_pattern_pool_has_no_prohibited_symbols` and
  `::test_generated_rsa_copy_has_no_prohibited_symbols` — ban Unicode category
  `So`/`Sk` (stars, checkmarks, emoji) in patterns + generated copy, while
  allowing currency/`+`/`/` and accented destination names.
- `::test_no_duplicate_headlines_in_long_name_discount_variant` — every variant's
  headlines must be unique case-insensitively.

### Residuals (non-blocking)

  systematic emitter bug (not 1-per-ad-group); likely specific restricted terms.
  Every ad group retains keyword coverage. Diagnose with the same

- **Generic sitelinks/callouts.** The live extensions are defaults ("About Us /
  Contact Us / Our Services / Get a Quote", "Fast Service / Free Quote / …") —
  `case.yaml` defines no travel-specific extension copy. Author real ones before
  any non-test use.
