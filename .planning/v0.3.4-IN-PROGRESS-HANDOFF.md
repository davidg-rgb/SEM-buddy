## 3. Mission 1 — Spell + ad-copy QA across all 4,580 RSAs

The four reviewer agents that ran end of last session only sampled **95 RSAs** (10 published + 85 from the new CSV stratified across 18 ad groups). The pattern-level findings have all been fixed, BUT individual destinations may still ship issues the sample didn't surface:

- **Spelling typos** — destination names sourced from XLSX may carry transcription errors (the source had at least one — `Mazow'iecki` with stray apostrophe was caught earlier). Run a spell-pass against all 4,580 RSAs.
- **Unnatural truncations** that survived the truncation guards (the v0.3.3 fix dropped known bad endings, but there's an unknown long tail).
- **Banned phrases in the LONG TAIL** — the agents looked for specific banned phrases; a fresh sweep may find ones not in the existing list.
- **Repetition across the 15 headlines of a single RSA** — currently no automated check exists; manually scanning 4,580 RSAs is impractical but a script + spawned agents can sample-check.
- **Cross-RSA semantic similarity** — Google's RSA optimizer dampens ad strength if two RSAs in the same ad group share too much copy. Sample-check ~50 ad groups.
- **Discount % rendering edge cases** — what does `discount_pct = 0.005` render as? `0%`? `1%`? Likely fine, but worth confirming.
- **Long-name destinations beyond the 18-char threshold** — the fallback policy is in place but the sample reviewers only saw a handful. Audit all destinations with name length ≥ 18.

## 4. Mission 2 — Mandatory discount headline per discounted destination

### The exact ask

> At least one headline per destination should be: `"Save up to [discount] on flights to [CITY CODE]"` where discount is applicable.

### Hard constraint: 30-char headline limit

The literal phrasing **does not fit**:
- `"Save up to 38% on flights to BKK"` = **32 chars** (over)
- `"Save up to 5% on flights to BKK"` = **31 chars** (over)
- `"Save up to 60% on flights to BKK"` = **32 chars** (over)
- Even with single-digit discount + 2-char SKU: `"Save up to 5% on flights to SF"` = **30 chars** (right at the limit — would fit but no margin)

### Three patterns that DO fit

Pick one (the closest-fitting, in priority order):

| Pattern | Example (38% to BKK) | Chars | Notes |
|---|---|---|---|
| `Save up to {pct}% to {sku}` | `Save up to 38% to BKK` | 21 | Tightest; drops "flights" but the destination is also pinned at H2 so context survives |
| `Save {pct}% on {sku} flights` | `Save 38% on BKK flights` | 23 | Drops "up to" — slightly more assertive |
| `{pct}% off flights to {sku}` | `38% off flights to BKK` | 22 | Number-led per First-Three-Words doctrine |

**Recommended: pattern #1** — closest to the brief's literal phrasing, keeps the "up to" hedge (which is the FTC-safe framing), fits all 963 destinations.

### Implementation

This pattern goes into the `discount_led` variant in `data/en/ad_copy_patterns.json`. The variant is already emitted only when `discount_pct >= 0.15` per the v0.3.3 floor — meaning the 215 low-discount-but-non-zero destinations (5–14% off) would NOT get this headline.

**LOCKED (operator-approved 2026-05-20):** "Where discount is applicable" = **`discount_pct >= 0.15`** — the same ~728 destinations that get the `discount_led` variant today. No change to the `MIN_DISCOUNT_PCT_FOR_DISCOUNT_LED` floor; no regression of the v0.3.3 CTR-negative-variant fix.

This means:
- 728 destinations (`discount_pct >= 0.15`) get the mandatory `"Save up to {pct}% to {sku}"` headline inside their `discount_led` variant.
- 215 destinations (`0 < discount_pct < 0.15`) do NOT get this headline — they continue shipping only 4 variants (no discount_led) per the v0.3.3 floor.
- 20 destinations (`discount_pct == 0`) also do NOT get this headline.

**Open sub-question for next session (not blocking Mission 2):** should the 215 low-discount destinations get their OWN mandatory CITY-CODE-anchored headline in a different variant (e.g., `loss_aversion` getting `"Lock {sku} from ${from_price}"`)? Operator can decide after seeing the v0.3.4 sample output.

## 5. Mission 3 — Per-variant `text=N` URL rotation

### The exact ask

> The different ad versions are labeled as `text=1`, `text=2`, `text=3` etc.

### Current behavior (v0.3.3)

`src/generators/campaign_builder.py::_build_ad_group_for_product` line ~475:
```python
if primary_url_template and cycler is not None:
    n = cycler.next()
    final_url = expand_url_template(primary_url_template, product, n=n)
```

`cycler.next()` is called **once per ad group**. All 4–5 variants for "Bangkok (BKK)" share `text=3` (say); all variants for "Tokyo (TYO)" share `text=4`. Variants are NOT distinguishable by `text=N`.

### Required behavior

Each variant within an ad group gets a different `text=N`:
- Variant 1 (price_led) → `text=1`
- Variant 2 (discount_led, when emitted) → `text=2`
- Variant 3 (social_proof) → `text=3`
- Variant 4 (urgency) → `text=4`
- Variant 5 (loss_aversion) → `text=5`

For products without `discount_led` (4 variants total): map variants to `text=1,3,4,5` (preserving the variant_role → N mapping) OR `text=1,2,3,4` (sequential). **Recommend sequential** (1,2,3,4) — keeps analytics tidy and tracks "which variant slot" rather than "which lever".

### Implementation sketch

1. In `src/generators/ad_copy_generator.py::generate_rsa_variants(...)`, accept a `final_url_template` instead of a pre-rendered `final_url`. For each variant index `i` (1-indexed), call `expand_url_template(template, product, n=i)` to build a per-variant URL.
2. In `src/generators/campaign_builder.py::_build_ad_group_for_product`, stop calling `cycler.next()` and instead pass the raw URL template through. The `NCycler` becomes unused for catalog mode — keep it for the legacy `_structure_by_service` path or delete if unused.
3. Verify the CSV exporter and live pusher already emit per-RSA `final_url` (they do — both iterate `ad.final_url`).
4. Update `tests/test_rsa_variants.py` and `tests/test_catalog_campaign_builder.py::test_each_ad_group_has_unique_final_url_with_n_rotation` to assert per-variant URLs.
