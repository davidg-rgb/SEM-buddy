## 1. Canonical case — Flightnetwork.com (etraveli)

**Source:** `clients/etraveli/Client Case Info/_Google Ads task (template)- David Geborek Wågestrand.docx`

### Data sources
- `Destination list (Template).xlsx` with 3 sheets:
  - **Destinations** (1,000 rows): `Destination name`, `Destination code` (3-letter IATA)
  - **From Prices** (965 rows): `Destination code`, `From price` (USD floats, e.g. 59.0)
  - **Discounts** (965 rows): `Destination code`, `Discount` (percentage as float, 0.0–?)
- Note: 35 destinations have NO price/discount entries — must be handled gracefully (no crash, sensible fallback in ad copy).
- Known data quality issues observed: typos (`Vinyard`→`Vineyard`, `Kamchats`→`Kamchatsky`), backtick instead of apostrophe in `Mazow\`iecki`, possible non-IATA codes mixed in. The brief explicitly requires cleaning.

### Required output
- **Account:** Create new Google Ads account `Etraveligroup Test account David Geborek Wågestrand`. Grant admin access to `klaus.thorup@etraveligroup.com` and `kasper.engelheim-hove@etraveligroup.com`.
- **Structure:** 1,000 destinations → campaigns/ad groups (right pattern: one parent campaign × many ad groups, OR thematic campaigns × 50–100 ad groups, NOT 1,000 campaigns).
- **Ads:** ≥ 1 RSA per destination, referencing the destination name + price + dynamic URL. English language.
- **Dynamic URLs:** `www.flightnetwork.com/from/google/rf/destination?to={CODE}&text={N}` where `{CODE}` is the IATA code and `{N}` cycles `1,2,3,…` for landing page variation.
- **Sitelinks:** relevant English sitelinks per campaign.
- **Promotion Extensions:** **one per destination** (≈1,000 of them), each interpolating the destination's discount/price.
- **Lead Form Extensions:** one per campaign.
- **Bidding:** flexible, ROI-positive (Target ROAS or Target CPA at campaign level), with discount-driven ad-group-level adjustments so destinations with bigger discounts get aggressive bids. Temporary "sales" mode = scheduled bid uplifts.
- **Validation:** every entity must be syntactically valid for Google Ads Editor import.

Each of these shapes the rest of the work. Confirm with the user at session start.

| # | Decision | Default proposal | Alternatives |
|---|---|---|---|
| AD1 | Catalog format on disk | YAML catalog config + Parquet/CSV data; lazily loaded | Pure JSON; SQLite; in-memory only |
| AD2 | Catalog row → ad group cardinality | 1 ad group per row (1 destination = 1 ad group) | Grouped (e.g. by continent/region) |

### C1. Catalog ingestion — multi-source loader with joining

**Effort:** ~3h · **Dependencies:** none · **Priority:** P0 (foundation)

**Problem.** No way to load a catalog dataset. The case provides one XLSX with 3 sheets that need joining by `Destination code`. Future cases may use Google Sheets URLs, CSVs, JSON arrays, or SQLite.

**Why it matters.** Every other catalog work item depends on this. Reusability: the same loader must accept hotel-room catalogs, product feeds, etc.

**Files to create.**
- `src/catalog/` (new package)
  - `__init__.py`
  - `loader.py` — `load_catalog(config: CatalogConfig) -> Catalog`
  - `models.py` — `CatalogConfig`, `Catalog`, `CatalogRow`
  - `sources.py` — `XlsxSource`, `CsvSource`, `JsonSource` (future)

**Approach.** Catalog config is YAML living at `clients/<slug>/catalog.yaml`:
```yaml
schema_version: 1
primary_key: code
sources:
  - type: xlsx
    path: "Client Case Info/Destination list (Template).xlsx"
    sheet: Destinations
    columns:
      name: "Destination name"
      code: "Destination code"
  - type: xlsx
    path: "Client Case Info/Destination list (Template).xlsx"
    sheet: "From Prices"
    join_key:
      source_column: "Destination code"
      target_column: code
    columns:
      from_price: "From price"
  - type: xlsx
    path: "Client Case Info/Destination list (Template).xlsx"
    sheet: Discounts
    join_key:
      source_column: "Destination code"
      target_column: code
    columns:
      discount_pct: "Discount"
defaults:
  from_price: null
  discount_pct: 0.0
```

`Catalog` is essentially a `list[CatalogRow]` where `CatalogRow` is `dict[str, Any]` with normalized keys.

**Tests.**
- Load 3-sheet XLSX, verify 1,000 rows in catalog
- Verify the 35 destinations without price entries get `from_price=None` (or default)
- CSV-only source works
- Missing required column raises clear error

### C2. Catalog validator + cleaner

**Effort:** ~2h · **Dependencies:** C1 · **Priority:** P0

**Problem.** Data has typos and possibly non-IATA codes. Brief requires "all entities … formatted correctly and any errors fixed. All destination codes should be 3-letters."

**Why it matters.** Wrong codes = broken URLs = ad disapprovals. Reusability: every catalog needs validation/cleaning.

**Files.**
- `src/catalog/validators.py`
  - `validate_iata_code(code: str) -> bool` (regex `^[A-Z]{3}$`)
  - `validate_catalog(catalog, schema: CatalogSchema) -> ValidationReport`
- `src/catalog/cleaners.py`
  - `clean_destination_name(name: str) -> str` (smart-quote normalize, ASCII fallback for backticks, etc.)
  - `clean_with_llm(rows: list[CatalogRow], fields: list[str]) -> list[CatalogRow]` (optional Claude CLI pass for fuzzy typo correction)

**Approach.** Two-phase. Phase 1: deterministic rule-based cleaning (regex, unicode normalization, backtick→apostrophe). Phase 2: optional LLM-assisted typo correction with structured JSON output and human-readable diff log. The LLM pass is gated on `SEM_DISABLE_LLM` and writes its diff to `clients/<slug>/catalog/cleaning_log.json` for audit.

**Tests.**
- Backtick → apostrophe (`Mazow\`iecki` → `Mazowiecki`)
- Truncated names flagged but not auto-fixed unless LLM enabled
- Non-IATA codes flagged in report
- Empty/missing required field surfaces as error, not silent drop
- LLM cleaner path: mock subprocess, verify diff log written

### C3. `Destination` / generic `Product` model + `_structure_by_sku` builder

**Effort:** ~4h · **Dependencies:** C1 · **Priority:** P0

**Problem.** `build_campaigns` today picks between service-mode (1 campaign per service) and geo-mode (1 campaign per geo). Neither handles 1,000-row catalogs. Naive scale-up = 1,000 campaigns, which is wrong.

**Why it matters.** The case is fundamentally a SKU-based catalog. Reusability: hotels, products, cruises, rentals — all are SKU-driven.

**Files.**
- `src/models/catalog.py` — `Product` model (formerly `Destination` for this case but generalized):
  ```python
  class Product(BaseModel):
      sku: str                          # IATA code for destinations
      name: str
      attributes: dict[str, Any] = {}   # from_price, discount_pct, etc.
      keywords: list[str] = []          # optional pre-seeded keywords
      url: HttpUrl | None = None        # resolved URL (post-templating)
  ```
- `src/generators/campaign_builder.py` — new `_structure_by_sku(client, products, config) -> list[Campaign]`:
  - One parent campaign by default
  - Optional `partition_by_attribute` config to split into N campaigns (e.g. by continent)
  - Each Product becomes one AdGroup with its own URL, keywords, RSA, promotion extension

**Approach.** Add a new field `structure_mode: Literal["service", "geo", "sku", "auto"] = "auto"` to a new `CampaignBuildConfig`. `auto` keeps current behavior; `sku` triggers the new path.

**Sample partitioning config:**
```yaml
structure:
  mode: sku
  partition_by_attribute: null   # OR "region", to split into N campaigns
  campaign_name_template: "Flightnetwork - All Destinations"
  ad_group_name_template: "{name} ({sku})"
```

**Tests.**
- 1,000-row catalog → 1 campaign × 1,000 ad groups (default)
- Partition by region → N campaigns (verify with fixture)
- Each ad group has the right URL, keywords, RSA
- Performance: build 1,000-product structure in < 30s with `SEM_DISABLE_LLM=1`

### C4. URL templating

**Effort:** ~1.5h · **Dependencies:** C3 (uses Product attributes) · **Priority:** P0

**Problem.** `final_url` is currently a static `HttpUrl`. The case needs `flightnetwork.com/from/google/rf/destination?to={CODE}&text={N}` with `N` cycling.

**Why it matters.** Every catalog campaign needs per-row URLs. Reusability: any client with parameterized landing pages.

**Files.**
- `src/catalog/url_templating.py`
  - `expand_url_template(template: str, product: Product, n: int = 1) -> str`
  - Supports `{sku}`, `{name}`, any `{attribute_name}`, and a magic `{N}` rotation counter
- Integration in `_structure_by_sku` and in `_promotion_rows` (C5).

**Approach.** Jinja-light templating (no full Jinja dep; just `str.format_map`). N-rotation is round-robin across a configurable range (1..5 by default) so 1,000 destinations cycle through 5 landing variants evenly.

**Catalog config addition:**
```yaml
url_templates:
  primary: "https://www.flightnetwork.com/from/google/rf/destination?to={sku}&text={N}"
  text_n_range: [1, 5]   # cycles 1..5
```

**Tests.**
- Template with `{sku}` substitutes correctly
- `{N}` rotation cycles across products
- Missing attribute raises clear error (not silent empty)
- Pydantic HttpUrl validates the expanded URL

**Problem.** Case requires 1,000 destination-specific promotion extensions. **No model exists.**

**Why it matters.** Promotion extensions surface price/discount above the ad, directly improving CTR. Reusability: any catalog with pricing/discount fields.

**Google Ads Editor CSV format (verified against Editor v2.5+):**

| Column | Sample value |
|---|---|
| Campaign | Flightnetwork - All Destinations |
| Ad group | Petropavlovsk-Kamchatsky (PKC) |
| Promotion target | (empty for ad-group level) |
| Discount modifier | UP_TO |
| Percent off | 25 |
| Money amount off | (or this — mutually exclusive with Percent off) |
| Promotion code | (optional) |
| Orders over amount | (optional) |
| Promotion start date | 2026-05-20 |
| Promotion end date | 2026-06-30 |
| Final URL | <templated URL> |
| Final URL suffix | (optional) |
| Tracking template | (optional) |
| Language | en |
| Occasion | (optional, e.g. SUMMER_SALE) |

**Files.**
- `src/models/campaign.py` — add `PromotionExtension`:
  ```python
  class PromotionExtension(BaseModel):
      campaign_name: str
      ad_group_name: str | None = None  # None = campaign-level
      discount_modifier: Literal["UP_TO", "NONE"] = "UP_TO"
      percent_off: float | None = None
      money_amount_off: float | None = None
      promotion_code: str | None = None
      orders_over_amount: float | None = None
      start_date: date | None = None
      end_date: date | None = None
      final_url: HttpUrl
      language: str = "en"
      occasion: str | None = None
      # validators: exactly one of percent_off / money_amount_off
  ```
- Add to `CampaignPlan.promotions: list[PromotionExtension]`
- `src/generators/promotion_extension_generator.py` — `generate_promotions(products, campaign_name, url_template) -> list[PromotionExtension]`
- `src/generators/csv_exporter.py` — new `_promotion_rows()` → `08_promotions.csv`
- Update README in `_README_CONTENT`

**Generator logic.** For each product with `discount_pct > 0`, emit a PromotionExtension with `percent_off = discount_pct`, URL templated, ad group = product's ad group. For products with `discount_pct = 0` or missing, skip (or emit money-off variant if `from_price` set and user opts in).

**Tests.**
- Catalog with 100 rows where 60 have discounts → 60 PromotionExtensions
- Pydantic validates "exactly one of percent_off / money_amount_off"
- CSV columns match Editor spec exactly (typo would silently fail import)
- URL is the templated one, not the campaign default

### C10. Ad-group-level bid modifier + rules engine

**Effort:** ~3h · **Dependencies:** C3 · **Priority:** P1 (case-required)

**Problem.** Case requires "discount-driven bidding" — destinations with bigger discounts should bid more aggressively. No ad-group-level bid modifier exists. Bid strategies are campaign-level only.

**Why it matters.** This IS the "granular bid control" the case asks for. Reusability: any catalog with a margin/discount/priority attribute.

**Files.**
- `src/models/campaign.py` — add to `AdGroup`: `bid_modifier: float = 1.0` (range 0.1–10.0) and `target_cpa_micros: int | None = None` (override)
- `src/catalog/bid_rules.py` — declarative rules:
  ```yaml
  bid_rules:
    - if: discount_pct >= 30
      then: { modifier: 1.5 }
    - if: discount_pct >= 15
      then: { modifier: 1.25 }
    - if: from_price < 100
      then: { modifier: 1.1 }
  ```
- `src/generators/campaign_builder.py` — apply rules to each ad group during `_structure_by_sku`
- `src/generators/csv_exporter.py` — extend `_ad_group_rows()` to emit `Max CPC` / `Bid modifier` columns

**Approach.** Rules are evaluated in order; the FIRST matching rule wins (consistent with Google Ads). Use safe expression evaluator (e.g. `simpleeval` or a hand-rolled DSL — DO NOT use `eval()`).

**Tests.**
- Product with `discount_pct=35` → ad group has `bid_modifier=1.5`
- Multiple matching rules — first wins
- Rules referencing missing attributes don't crash, just don't fire
- CSV column has correct format (Google Ads expects integers like `+50%` or floats `1.5`)

## 7. Reusability requirements

The whole point of building this rather than scripting the case once. The next case must require **only** these touchpoints from the operator:

1. New folder `clients/<slug>/`
2. Drop the source XLSX/CSV into `clients/<slug>/data/`
3. Write `clients/<slug>/catalog.yaml` (~20 lines)
4. Write `clients/<slug>/case.yaml` (~50 lines)
5. Run `sem case run <slug>`

No code changes. No new templates required (English pack covers most travel/ecom; new pattern packs added only when the client's language isn't English/Swedish).

**Anti-goals.** Don't hardcode "flightnetwork" or "destination" or "IATA" anywhere in `src/`. Catalog is generic. Code must work for: hotels, cruises, car rentals, e-com products, real-estate listings.

## 8. Resolved decisions (confirmed 2026-05-20)

**These were pre-answered by the user before the session was cleared. Do NOT re-ask — proceed with the answers below. If implementation reveals a problem with a given choice, flag it explicitly and propose a revision.**

1. **Account creation via API** — **YES, build C12 + C13.** Rationale: user explicitly wants reusability across future cases ("we can reuse the build to do it again within any time frame"). Manual UI creation defeats that.

2. **AD1 catalog format** — **YAML config + raw data files (XLSX/CSV).** Acceptable as proposed in section 3. Config is human-readable; data files stay in their native format.

3. **AD4 multi-language** — **Both: static language packs as baseline + LLM enrichment on top.** Mirrors the existing Swedish setup. Static pack provides deterministic floor (works offline, works in CI with `SEM_DISABLE_LLM=1`); LLM enrichment adds polish when available. `data/en/` ships with the v0.3 work.

4. **AD5 bid rules** — **Declarative YAML, first-match-wins.** Arithmetic DSL is YAGNI for v0.3. If a future case genuinely needs `modifier: 1 + (discount_pct / 100)` we revisit then. For now: discrete bands (`discount_pct >= 30 → 1.5`, `>= 15 → 1.25`, etc.) are sufficient.

5. **C2 cleaning — human approval gate** — **YES.** Workflow:
   - `sem catalog clean <slug>` runs the cleaner, writes proposed fixes to `clients/<slug>/catalog/cleaning_log.json` AND a human-readable `cleaning_diff.md` alongside it. Does NOT modify the source data.
   - User reviews the diff, optionally edits it.
   - `sem catalog accept-fixes <slug>` applies the approved diff to a new file `clients/<slug>/catalog/cleaned.{xlsx,csv}`, leaving the original untouched.
   - Subsequent `sem case run` uses `cleaned.*` if present, falling back to original otherwise.

6. **Scale of first run** — **Start with 50 rows, then scale to full 1,000.** Test fixtures use the 10-row sample; first real run pulls a 50-row sample from the head of the actual XLSX (`Destination list (Template).xlsx[:50]`); only after C14 passes do we run the full 1,000. Reduces feedback cycle from minutes to seconds during Phase 1–2 work.

7. **Test data fixture redistribution** — **YES, sanitized.** The source file is literally a template ("the numbers are not real" per the brief). Take 10 representative rows from the destinations sheet (mix of clean names, typo cases, missing-data cases), replace prices/discounts with synthetic values that preserve the shape (e.g. random ints in `[50, 500]` for price, `[0, 50]` for discount). Save as `tests/fixtures/catalog_sample.xlsx`. Include in version control.
