# Domain Pitfalls

**Domain:** Swedish SEM campaign tool — polish milestone
**Researched:** 2026-03-06

---

## Critical Pitfalls

Mistakes that cause corrupt output or require rework across many files.

### Pitfall 1: ASCII Swedish in Data Files (Diacritics Silently Stripped)

**What goes wrong:** JSON data files contain `"Fa offert"` instead of `"Få offert"`, `"tjanster"` instead of `"tjänster"`, `"lon"` instead of `"lön"`. These propagate into ad copy, reports, and CSV exports. Google Ads serves ads with misspelled Swedish — users see broken text and CTR drops.

**Why it happens:** The original code was generated by AI agents that either used ASCII-only encoding or stripped diacritics during generation. Python 3 handles UTF-8 natively, but if the *source data* was never correct, the pipeline faithfully outputs garbage.

**Affected files (confirmed):**
- `data/swedish/cta_phrases.json` — "Fa" not "Få", "Begar" not "Begär", "Bestall" not "Beställ", "Kop" not "Köp", "Lagg" not "Lägg"
- `data/swedish/negative_keywords.json` — "tjanster" not "tjänster", "anstallning" not "anställning", "karriar" not "karriär", "lon" not "lön", "sjalv" not "själv"
- `src/generators/report_generator.py` — hardcoded Swedish strings throughout: "for" not "för", "pa" not "på", "sokord" not "sökord", "mal" not "mål", "narvaro" not "närvaro", "overvakning" not "övervakning"

**Consequences:** Every deliverable the tool produces (CSV, report, XLSX) contains misspelled Swedish. Client-facing output is unprofessional. Search ads may not match user queries properly.

**Prevention:**
1. Fix all data files first — this is the foundation everything else builds on
2. Add a CI/validation check: scan all `.json` files and string literals for known ASCII-Swedish patterns (e.g., regex `\b(Fa|fa|sokord|tjanst|karriar|lon)\b`)
3. Use `encoding="utf-8"` explicitly on all file I/O (already done in some places)
4. Never trust AI-generated Swedish text without manual review of diacritics

**Detection:** Search for common ASCII-Swedish patterns: words containing "sj" where "själv" is expected, "a" where "å/ä" is expected, "o" where "ö" is expected. A simple word-list validator catches 90% of cases.

**Confidence:** HIGH — verified by reading actual project files.

### Pitfall 2: Compound Word Splitter Only Handles Suffixes, Misses Prefixes and Interfixes

**What goes wrong:** The current `split_compound_word()` in `swedish_nlp.py` only checks a hardcoded list of 18 suffixes. It misses:
- Compounds where the meaningful part is a prefix (e.g., "bilverkstad" — it finds "verkstad" but "bil" is the domain-critical keyword)
- The binding morpheme "-s-" is stripped but other Swedish interfixes are ignored (Swedish also uses -e-, -o-, -u- interfixes in some compounds, though -s- is the most common)
- Three-part compounds (e.g., "företagskonsulttjänst") — only one split is attempted
- Compounds not ending in any of the 18 hardcoded suffixes

**Why it happens:** A suffix-matching heuristic is the simplest approach. Real Swedish decompounding requires a dictionary/lexicon or statistical model.

**Consequences:** Keyword expansion misses valid search terms. If a user searches "bilverkstad" and the splitter correctly finds "verkstad" but the keyword generator doesn't also generate "bil" + "verkstad" as a phrase, coverage suffers.

**Prevention:**
1. Use a dictionary-based approach: load a Swedish word list (SAOL or similar) and find the longest valid prefix + suffix combination
2. Handle the -s- interfix explicitly (already partially done) but also handle truncation patterns (e.g., "skola" becomes "skol-" in compounds)
3. Support recursive splitting for 3+ part compounds
4. For SEM purposes, over-splitting is better than under-splitting — false positives in keyword expansion are filtered by Google Ads, but missed keywords are lost forever

**Detection:** Test against a known list of 50+ Swedish compound words with expected splits. Compare output to expected results.

**Confidence:** HIGH — verified by reading `swedish_nlp.py:38-59`.

**Sources:**
- [Compound words and joint morphemes in Swedish](https://duolinguists.wordpress.com/2022/03/04/compound-words-and-joint-morphemes-in-swedish/)
- [Findwise: Compound word splitting - Swedish](https://findwise.com/labs/sample/compound-word-splitting-swedish)

### Pitfall 3: Google Ads Editor CSV Column Names Must Be Exact

**What goes wrong:** Google Ads Editor silently ignores rows or columns with wrong names. The CSV imports with zero errors but campaigns are missing data. Common mistakes:
- Using "Keyword Type" instead of "Criterion Type"
- Using "Ad Group Status" vs "Status" (context-dependent)
- Case sensitivity in bid strategy names (portfolio strategies are case-sensitive)
- Missing "Row Type" column or using wrong row type values

**Why it happens:** Google Ads Editor documentation is sparse about exact column names. The Editor doesn't report "column not recognized" — it just skips it.

**Consequences:** Campaigns import but are incomplete. Keywords may be missing match types, ads may lack pinning, extensions may not associate with campaigns.

**Prevention:**
1. Export a test campaign FROM Google Ads Editor first, then use those exact column names as the template
2. Build validation that imports the generated CSV back into a test account
3. The current `csv_exporter.py` uses "Row Type" which is correct for the multi-row format, but the column names should be verified against a known-good export
4. Test with a real Google Ads Editor import after any column name changes

**Detection:** Import the CSV into Google Ads Editor and check that the entity count matches expectations (campaigns, ad groups, keywords, ads, extensions).

**Confidence:** MEDIUM — based on Google's official documentation and community reports. Exact column names need verification against a real export.

**Sources:**
- [Google Ads Editor: Prepare a CSV file](https://support.google.com/google-ads/editor/answer/56368)
- [Google Ads Editor: CSV file columns](https://support.google.com/google-ads/editor/answer/57747)

## Moderate Pitfalls

Mistakes that cause delays, broken tests, or technical debt.

### Pitfall 4: Retrofitting Tests onto Tightly Coupled Code

**What goes wrong:** Adding tests to code that was never designed for testing leads to:
- Tests that require complex setup (real file paths, real API keys, full object graphs)
- Mocking so extensive that tests verify mock behavior, not real behavior
- Tests that break when internal implementation changes, providing no refactoring safety
- Testing the "happy path" only because the code has no error handling to test

**Why it happens:** Code written without tests tends to have hidden dependencies (global state, file system access, hardcoded paths). The `swedish_nlp.py` module uses `Path(__file__).resolve()` for data paths and module-level globals — both patterns that make testing harder.

**Prevention:**
1. Start with integration tests (CSV exporter produces valid CSV, compound splitter handles known words) before unit tests
2. Extract configuration (file paths, constants) into parameters rather than hardcoded values
3. Use `tmp_path` pytest fixture for file-based tests
4. Don't mock what you can construct — build real `CampaignPlan` objects using Pydantic factories rather than mocking
5. Prioritize testing the highest-value code first: CSV exporter and compound splitter, not internal helpers

**Detection:** If a test file is longer than the module it tests, or if `@patch` appears more than 3 times in a single test, the code needs refactoring before more tests.

**Confidence:** HIGH — well-established testing wisdom, verified against project structure.

**Sources:**
- [Python Testing Best Practices 2025](https://danielsarney.com/blog/python-testing-best-practices-2025-building-reliable-applications/)
- [pytest Good Integration Practices](https://docs.pytest.org/en/stable/explanation/goodpractices.html)

### Pitfall 5: Diacritics Map Has Duplicate Key Bug

**What goes wrong:** In `swedish_nlp.py:62-69`, the `_DIACRITICS_MAP` dictionary has duplicate keys:
```python
_DIACRITICS_MAP = {
    "a": "å",   # first assignment
    "å": "a",
    "o": "ö",
    "ö": "o",
    "a": "ä",   # OVERWRITES "a": "å" above!
    "ä": "a",
}
```
The key `"a"` maps to `"ä"` (last write wins), so the `"a" -> "å"` mapping is lost. The `generate_diacritics_variants` function works around this with a separate `replacements` list, but the `_DIACRITICS_MAP` dict is broken and would produce wrong results if used directly.

**Why it happens:** Python dicts don't raise errors on duplicate keys. The original author likely didn't notice.

**Prevention:**
1. Remove the broken `_DIACRITICS_MAP` dict entirely — it's not used by `generate_diacritics_variants` (which uses its own inline list)
2. If a bidirectional map is needed, use a list of tuples: `[("a", "å"), ("a", "ä"), ("o", "ö")]`
3. Add a linter rule or test that catches dict literal duplicate keys (pylint W0199)

**Detection:** Static analysis (pylint catches this as W0199 / `duplicate-key`).

**Confidence:** HIGH — verified by reading `swedish_nlp.py:62-69`.

### Pitfall 6: CSV Exporter Mixes Row Types in Single DataFrame

**What goes wrong:** The current `csv_exporter.py` puts campaigns, ad groups, keywords, ads, sitelinks, and callouts all in one DataFrame. Each row type has different columns, so the output CSV has many empty cells. Google Ads Editor can handle this (it uses "Row Type" to distinguish), but:
- Pandas `fillna("")` converts numeric columns to strings
- Column ordering is non-deterministic if different row types introduce columns in different orders
- Debugging import failures is hard when every row has 30+ mostly-empty columns

**Why it happens:** Using a single DataFrame is the simplest implementation. It works for small campaigns but becomes unwieldy.

**Prevention:**
1. Verify column ordering matches Google Ads Editor expectations (campaign-level columns first)
2. Add explicit column ordering in the exporter: `df = df[ordered_columns]`
3. Consider whether Google Ads Editor prefers one CSV per entity type or a single combined CSV (both are supported, but separate files are easier to debug)
4. Add a round-trip test: export, then parse the CSV and verify entity counts

**Detection:** Open the generated CSV in Google Ads Editor and verify all entities are recognized.

**Confidence:** MEDIUM — the single-DataFrame approach works but has known fragility.

### Pitfall 7: Markdown-to-PDF Rendering Drops Swedish Characters

**What goes wrong:** When converting the markdown strategy report to PDF:
- Default fonts in PDF libraries (Helvetica, Courier) don't include å, ä, ö glyphs
- Characters render as empty boxes, question marks, or are silently dropped
- HTML-to-PDF pipelines may double-encode UTF-8 if intermediate steps assume Latin-1

**Why it happens:** PDF is not a text format — it embeds font subsets. If the font doesn't include Swedish glyphs, they can't be rendered. Libraries like fpdf2 require explicitly loading a Unicode-capable font.

**Prevention:**
1. Use a library that handles Unicode natively (WeasyPrint, or fpdf2 with explicit Unicode font loading)
2. Always embed fonts that include Latin Extended characters (DejaVu Sans, Noto Sans, or any font with full Latin-1 coverage)
3. Test PDF output with a string containing all Swedish special characters: `"Å Ä Ö å ä ö — test"`
4. If using fpdf2, call `add_font()` with a `.ttf` file before any text output; the built-in fonts are ASCII-only

**Detection:** Open the generated PDF and search for å, ä, ö. If the search finds nothing but the source markdown contains them, font embedding failed.

**Confidence:** MEDIUM — based on fpdf2 documentation and WeasyPrint issue reports.

**Sources:**
- [fpdf2: Fonts and Unicode](https://py-pdf.github.io/fpdf2/Unicode.html)
- [WeasyPrint font issues](https://github.com/Kozea/WeasyPrint/issues/1318)

## Minor Pitfalls

Mistakes that cause annoyance but are fixable quickly.

### Pitfall 8: Google Ads Headline/Description Character Limits Count Bytes Differently

**What goes wrong:** Google Ads limits headlines to 30 characters and descriptions to 90 characters. The current `count_display_chars()` function uses `len(text)`, which is correct for Swedish (å, ä, ö are single characters in Python). However:
- Some ad copy generators may count bytes instead of characters (1 å = 2 bytes in UTF-8)
- Emoji or special punctuation (em dash, curly quotes) may count as 1 or 2 characters depending on the API

**Prevention:** The current implementation is correct. Keep using `len()` for character counting. Add a test that verifies `count_display_chars("Få offert idag")` returns 14 (not 15 or 16).

**Confidence:** HIGH — Google Ads counts Unicode code points, not bytes.

---

### Pitfall 9: Report Generator Mixes Swedish and English Section Headers

**What goes wrong:** The report in `report_generator.py` uses English headers ("Executive Summary", "Business Analysis", "Campaign Structure") but Swedish body text. This is inconsistent and confusing for Swedish-speaking clients.

**Prevention:** Decide on one language for the report. For a Swedish market tool, use Swedish headers: "Sammanfattning", "Affärsanalys", "Kampanjstruktur", etc. Or use English headers if the report audience includes non-Swedish stakeholders.

**Confidence:** HIGH — verified by reading `report_generator.py`.

### Pitfall 10: No Git History Makes Regression Detection Impossible

**What goes wrong:** Without version control, there's no way to:
- Identify when a bug was introduced
- Revert a broken change
- Review what changed between working and broken states
- Collaborate safely (two people editing the same file)

**Prevention:**
1. Initialize git before making any polish changes
2. Commit the current state as-is (warts and all) as the baseline
3. Make each fix (diacritics, compound splitter, CSV columns) as a separate commit
4. This also enables CI/CD for running tests on every change

**Confidence:** HIGH — fundamental software practice.
